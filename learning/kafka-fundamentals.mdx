## Topic

**The hook:** a topic is a named, append-only log file. Think of a spreadsheet you can only ever add rows to — never edit a row, never delete one in place. That is the whole thing. No schema enforcement, no query engine, just an ordered sequence of records with a name.

It exists as the unit of organisation. Producers write to a topic; consumers read from a topic. One topic equals one category of event stream.

<Note>
**CDC consequence.** Debezium gives each captured table its own topic, named `<server>.<schema>.<table>`. An insert, update or delete on `claim` becomes a new record appended to that table's log. Two source databases with four tables each means eight topics, at minimum.
</Note>

A topic by itself is not the unit of ordering or parallelism. That is the next concept.

## Partition and offset

A topic is not really one log — it is split into N ordered logs called **partitions**. A filing cabinet, with partitions as the individual drawers. Each drawer has its own strict sequence; there is no ordering *across* drawers.

Each record in a partition gets an **offset** — its position number in that drawer: 0, 1, 2, 3. Offsets only mean something within their own partition. Offset 5 in partition 0 and offset 5 in partition 1 are unrelated records.

**Why partitions exist:** parallelism. A single log can only be read by one consumer at a time if order is to be preserved. Splitting a topic across partitions lets multiple consumers read different partitions simultaneously. This is Kafka's main scaling lever.

## Broker

Forget replication exists for a moment.

A **broker** is a machine, or a process, running Kafka. Three brokers means three servers.

Say the `claim` topic has six partitions. Kafka spreads them across the brokers so no single machine holds everything:

| Broker | Holds |
| --- | --- |
| Broker-1 | P0, P3 |
| Broker-2 | P1, P4 |
| Broker-3 | P2, P5 |

That is the entire idea: a server that physically stores some partitions and serves reads and writes for them. Storage and load, spread across machines.

<Warning>
**In that picture, if Broker-1 dies, P0 and P3 are gone.** Not temporarily unavailable — gone, unless the disk itself is recovered. That is real data loss in your CDC stream.

This is precisely the problem replication solves, and the reason nobody runs a replication factor of 1 in production, MSK included.
</Warning>

## Replication

Replication is a separate decision from partition placement: *how many copies of each partition do I want, in case a machine dies?*

With **replication factor 3**, partition P0 does not only live on Broker-1 — its data is copied onto two other brokers as well. Never twice on the same broker; that would defeat the point.

One of those copies is the **leader**. All reads and writes for P0 go to the leader specifically. The other two **follower** copies passively replicate whatever the leader has. They serve no traffic; they sit there as backup.

When Broker-1 dies, P0's leader is gone — but an up-to-date copy exists elsewhere, so Kafka promotes one of them to leader. No data lost, a brief blip in availability.

<Tip>
**Interview flag — asked constantly at senior level.** *"What happens to a partition's leader when its broker fails?"*

Sharp answer: the controller — in KRaft, one of the brokers itself, no separate ZooKeeper — detects the failure through missed heartbeats and promotes one of the **in-sync replicas (ISR)**, meaning a follower that was fully caught up, to leader.

Follow-up: *"can you lose data during this?"* Honest answer: it depends on the producer's `acks` setting and the topic's `min.insync.replicas`. Knowing the term ISR and that the answer is conditional is what separates a real answer from a memorised one.
</Tip>

## KRaft

**KRaft** (Kafka Raft) is Kafka's built-in consensus protocol, which replaced ZooKeeper.

Before it, Kafka needed a separate ZooKeeper cluster to track cluster metadata — which brokers exist, who leads which partition, configuration — and to elect a controller. KRaft moves that job inside Kafka: a subset of brokers form a Raft quorum that agrees on and stores the metadata directly.

Net effect: one less system to operate, faster controller failover, and it is the default in Kafka 3.x and on MSK.

<Note>
This project's cluster runs KRaft, so ZooKeeper never appears. In an interview it is worth one sentence only — *"KRaft replaced ZooKeeper for cluster metadata and controller election"* — and nothing more.
</Note>

## Producers and keys

When a producer sends a record it may attach a **key** — just bytes, often a string such as a claim ID. Kafka hashes the key, takes it modulo the partition count, and that picks the partition.

Same key → same hash → same partition, every time, as long as the partition count does not change.

<Columns cols={2}>
  <Card title="No key" icon="shuffle">
    Records spread round-robin across partitions. Good for load balancing, useless for ordering.
  </Card>
  <Card title="With a key" icon="key">
    Every record with that key lands in the same partition — and within a partition, order is strictly preserved.
  </Card>
</Columns>

**This is the only ordering guarantee Kafka gives.** Kafka never promises that all records across a topic arrive in the order they were produced. It promises only that records sharing a key, and therefore a partition, arrive in order. There is no global ordering — not even on a single-partition topic, once you consider that partition counts change.

<Note>
**CDC consequence.** Debezium keys every change event by the source row's primary key. Every insert, update and delete for claim 4457 hashes to the same partition and arrives in order. A different claim is a different key and possibly a different partition — with no ordering relationship between them, which is fine, because they are independent rows.

Without a key, three updates to policy 7 could land in three partitions, and the sink could apply update 3 before update 1 — corrupting the final state in Snowflake.
</Note>

<Tip>
**Interview flag.** *"How does Kafka guarantee ordering?"* The wrong answer is "Kafka preserves message order."

Sharp answer: *"Kafka preserves order only within a partition, and the producer chooses the partition through the key — so ordering is a partitioning design decision, not something Kafka gives you for free."*
</Tip>

## Consumer groups and offset commits

Think of a partition as a single-lane road and a **consumer group** as one crew assigned to drive it. Kafka guarantees that only one consumer within a group reads a given partition at a time. Six instances against a six-partition topic means each instance owns exactly one partition, in parallel, with no overlap.

As a consumer processes records it periodically tells Kafka *"I have processed up through offset N"* — an **offset commit**. Kafka stores these in an internal topic, `__consumer_offsets`. After a crash the consumer resumes from its last committed offset, so anything read but not yet committed is processed again.

This is a knob you control: commit after every record (slow, very safe) or commit in batches (fast, a crash replays a small batch).

<Note>
**CDC consequence.** Your S3 sink connector is a consumer. If it crashes after writing Parquet files but before committing offsets, it re-reads and re-writes those same events on restart. The Snowflake load must therefore tolerate duplicates — normally a `MERGE` on primary key plus change timestamp. This is what **at-least-once** delivery means in practice.
</Note>

## Check yourself

Answer before expanding.

<AccordionGroup>
  <Accordion title="Six partitions, three consumer instances in the group. How are partitions divided? Then you scale to eight instances — what happens to the extra two?">
    Kafka assigns two partitions to each of the three consumers. Each instance reads its two partitions independently.

    Scaling to eight instances against six partitions leaves **two consumers completely idle**. A partition is assigned to at most one consumer in a group, so consumer count above partition count buys nothing.

    The practical rule: **partition count is the ceiling on consumer parallelism.** You choose the partition count when you create the topic, and raising it later breaks key-to-partition stability — so it is a capacity decision made up front, not tuned later.
  </Accordion>

  <Accordion title="Debezium emits a change event with a null key. What breaks?">
    Records round-robin across partitions instead of landing in one. Three updates to policy 7 could land in three different partitions, and the sink consumer could process update 3 before update 1 — leaving the wrong final state in Snowflake, with no error anywhere to tell you.
  </Accordion>

  <Accordion title="Why are offsets in different partitions unrelated?">
    Each partition maintains its own independent sequence starting at 0. There is no shared counter or clock across partitions, which is exactly why there is no ordering guarantee across them.
  </Accordion>

  <Accordion title="Replication factor 1, three brokers. A broker dies. What is the state?">
    Every partition that broker held is unavailable until it returns, and if the disk is lost the data is lost. No copies exist anywhere else. Treated as data loss risk in production.
  </Accordion>
</AccordionGroup>

## Hands-on

<Warning>
Do these. Reading the section above and skipping this is how the concepts evaporate by next week.
</Warning>

All commands run against the local cluster. The Kafka CLI scripts live at `/opt/kafka/bin/` inside the `apache/kafka` image.

<Steps>
  <Step title="List what already exists">
    ```powershell
    cd D:\claims-platform\Infra
    docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
    ```

    You should see Kafka Connect's three internal topics and nothing else yet.
  </Step>

  <Step title="Create a topic with three partitions">
    ```powershell
    docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 `
      --create --topic demo.claims --partitions 3 --replication-factor 1

    docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 `
      --describe --topic demo.claims
    ```

    Read the `describe` output carefully — it names the leader and the replica list for each partition. On a single-broker cluster every leader is broker 1, which is why replication cannot be demonstrated locally.
  </Step>

  <Step title="Produce with keys and watch the partitioning">
    ```powershell
    docker compose exec -it kafka /opt/kafka/bin/kafka-console-producer.sh `
      --bootstrap-server localhost:9092 --topic demo.claims `
      --property parse.key=true --property key.separator=:
    ```

    Type these, one per line:

    ```
    claim-1:opened
    claim-2:opened
    claim-1:assigned
    claim-1:settled
    claim-2:rejected
    ```

    Then in a second terminal:

    ```powershell
    docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh `
      --bootstrap-server localhost:9092 --topic demo.claims --from-beginning `
      --property print.key=true --property print.partition=true
    ```

    **What to look for:** every `claim-1` record sits in the same partition, in the order you typed them. `claim-2` may be in a different partition. That is the ordering guarantee, visible.
  </Step>

  <Step title="Produce without a key and compare">
    Run the producer again without the two `--property` flags, send five messages, and consume with `print.partition=true`. The records scatter across partitions. This is the failure mode a null-keyed Debezium event would cause.
  </Step>

  <Step title="Watch a consumer group and its offsets">
    ```powershell
    docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh `
      --bootstrap-server localhost:9092 --topic demo.claims --group demo-group

    docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh `
      --bootstrap-server localhost:9092 --describe --group demo-group
    ```

    The `describe` output shows, per partition, the current offset, the log-end offset, and the **lag** between them. Lag is the single most important operational metric for a CDC pipeline — it is how you know whether the warehouse is keeping up.
  </Step>

  <Step title="Kill a consumer mid-stream">
    Start the group consumer, produce a burst of messages, `Ctrl+C` the consumer, then restart it with the same `--group`.

    It resumes from the last committed offset rather than from the beginning — and you will likely see a few records repeated. That repetition **is** at-least-once delivery, and it is why the Snowflake load must use `MERGE`.
  </Step>

  <Step title="Clean up">
    ```powershell
    docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 `
      --delete --topic demo.claims
    ```
  </Step>
</Steps>

You are ready to move on to Kafka Connect when you can explain, without looking: why `claim-1` records stayed in one partition, what consumer lag measures, and why restarting a consumer replayed a few records.
