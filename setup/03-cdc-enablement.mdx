The schema file built the house. This file installs the cameras.

Each database has its own `02_cdc.sql`, and both do the same three things.

## Step 1 — Decide how much history each table records

```sql
ALTER TABLE claim                REPLICA IDENTITY FULL;
ALTER TABLE adjuster             REPLICA IDENTITY FULL;
ALTER TABLE claim_status_history REPLICA IDENTITY DEFAULT;
ALTER TABLE claim_transaction    REPLICA IDENTITY DEFAULT;
```

`FULL` records the entire old row on update and delete; `DEFAULT` records only the primary key. Mutating tables get `FULL`; append-only ledgers get `DEFAULT`.

The full reasoning and cost analysis is in [Replica Identity](/concepts/replica-identity).

## Step 2 — Declare which tables may be replicated

```sql
CREATE PUBLICATION dbz_claims
    FOR TABLE claim, claim_status_history, claim_transaction, adjuster;
```

A publication is a named list of tables eligible for logical replication. Debezium will reference this publication by name in its connector configuration.

<Warning>
A table missing from the publication is invisible to CDC — no error, no warning, it simply never produces events. When someone reports "the new table isn't coming through", this is the first thing to check.
</Warning>

## Step 3 — Create the account Debezium logs in as

```sql
CREATE ROLE dbz WITH REPLICATION LOGIN PASSWORD 'dbz';
GRANT USAGE ON SCHEMA public TO dbz;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO dbz;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO dbz;
```

<ParamField path="REPLICATION" type="privilege">
Allows the role to open a replication slot and stream WAL. Without it, Debezium cannot start.
</ParamField>

<ParamField path="SELECT on all tables" type="privilege">
Needed for the **initial snapshot** — before streaming begins, Debezium reads existing rows directly so the warehouse starts with complete history rather than only changes made from today onward.
</ParamField>

<ParamField path="ALTER DEFAULT PRIVILEGES" type="privilege">
Makes future tables readable automatically. Without it, every new table would need a manual `GRANT`, and someone would eventually forget.
</ParamField>

<Note>
Debezium is given a dedicated role with read and replication rights only — never the superuser account. It never writes to the source database. This separation is the first thing a security reviewer looks for.
</Note>

## What this stage does not do

At the end of this stage, capture is *possible* but not yet *running* — there is no replication slot.

```sql
SELECT slot_name, plugin, active FROM pg_replication_slots;
```

Run immediately after the schema and CDC scripts, this returns **zero rows**. Publications and `wal_level` make capture possible; the slot is what makes it happen, and **Debezium creates the slot when a connector is registered**.

<Note>
Once the connectors are registered in [Kafka and Debezium](/setup/05-kafka-and-debezium), the same query returns one slot per database, plugin `pgoutput`, `active = true`. That is the moment WAL retention — and recording — begins.
</Note>
