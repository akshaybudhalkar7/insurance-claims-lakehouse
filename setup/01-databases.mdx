## Why two databases and not two schemas

Policy administration and claims are separate systems in every real insurer — different vendors, different teams, often different countries. Modelling them as two schemas in one database would quietly remove the hardest part of the problem: **you cannot join across them at the source, and you cannot enforce a foreign key between them.**

Keeping them genuinely separate forces the pipeline to solve the real problem, and gives the project something honest to say in an interview.

## The Compose file

Both services are defined in `Infra/docker-compose.yml`, using the same shape:

```yaml Infra/docker-compose.yml
services:
  postgres_policy:
    image: postgres:16
    container_name: postgres_policy
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: policy_admin
    ports:
      - "5433:5432"
    command:
      - postgres
      - -c
      - wal_level=logical
      - -c
      - max_replication_slots=4
      - -c
      - max_wal_senders=4
      - -c
      - wal_sender_timeout=0
    volumes:
      - ../sql/policy_admin:/docker-entrypoint-initdb.d
      - pgdata_policy:/var/lib/postgresql/data
    networks:
      - claims_net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d policy_admin"]
      interval: 10s
      timeout: 5s
      retries: 5
```

`postgres_claims` is identical apart from the database name, the port, and the SQL folder it mounts.

## What each part is doing

<AccordionGroup>
  <Accordion title="The command block" icon="terminal">
    This is the important part and the easiest to get wrong. `wal_level` cannot be changed with a SQL statement — it requires a server restart, so it is passed as a startup flag.

    Without `wal_level=logical`, everything else in this project is impossible: Debezium will connect, then fail with an error about logical decoding not being available.
  </Accordion>
  <Accordion title="Port mapping" icon="plug">
    `"5433:5432"` means *port 5433 on your machine forwards to 5432 inside the container*. Postgres always listens on 5432 internally; the two containers are separated by which host port they expose.

    | Database | Host port |
    | --- | --- |
    | `policy_admin` | 5433 |
    | `claims` | 5434 |

    Neither is on 5432. This trips people up constantly when connecting a client.
  </Accordion>
  <Accordion title="The init volume" icon="folder-open">
    Anything mounted at `/docker-entrypoint-initdb.d` is executed **once**, in filename order, the first time the database is created. That is why the SQL files are numbered `01_` and `02_` — schema before CDC configuration.

    Because it runs only on first creation, editing those files later does nothing until the data volume is removed.
  </Accordion>
  <Accordion title="The named volume" icon="hard-drive">
    `pgdata_policy:/var/lib/postgresql/data` keeps the actual data outside the container, so `docker compose down` and back up does not wipe the database.

    To genuinely start over you need `docker compose down -v` — the `-v` removes the volumes and lets the init scripts run again.
  </Accordion>
  <Accordion title="The shared network" icon="network-wired">
    Both containers sit on `claims_net`. Containers on the same network reach each other by service name — Debezium will connect to `postgres_policy:5432`, not `localhost:5433`. Inside the network, the internal port is what counts.
  </Accordion>
</AccordionGroup>

## Starting them

```powershell
cd D:\claims-platform\Infra
docker compose up -d
docker compose ps
```

Both containers should report `healthy`. If they report `starting` for more than a minute, check the logs:

```powershell
docker compose logs postgres_policy
```

<Check>
Confirm logical replication is actually active — this is the single most important check at this stage:

```sql
SHOW wal_level;
```

It must return `logical`. If it returns `replica`, the `command:` block did not take effect.
</Check>
