## The mental picture

<CardGroup cols={2}>
  <Card title="WAL — the diary" icon="book">
    Postgres writes every change to a Write-Ahead Log before applying it. This is how it survives a crash. Always on, in every Postgres installation.
  </Card>
  <Card title="wal_level=logical — plain language" icon="language">
    By default the diary is written in shorthand about disk blocks — useless for CDC. Setting `logical` makes Postgres also record *which row in which table changed, and to what*.
  </Card>
  <Card title="Publication — the guest list" icon="list-check">
    Names the tables eligible for replication. A table not in a publication is invisible to CDC, even with `wal_level=logical` set.
  </Card>
  <Card title="Replication slot — the bookmark" icon="bookmark">
    Tracks how far a consumer has read, and **prevents Postgres from deleting WAL past that point**. This is what guarantees no change is lost while a consumer is offline.
  </Card>
</CardGroup>

## How they were configured here

`wal_level` is set in the container startup command, not in a SQL file, because it requires a server restart:

```yaml Infra/docker-compose.yml
command:
  - postgres
  - -c
  - wal_level=logical
  - -c
  - max_replication_slots=4
  - -c
  - max_wal_senders=4
  - -c
  - wal_sender_timeout=0
```

<ParamField path="wal_level=logical" type="setting">
Makes WAL entries rich enough to reconstruct row-level changes.
</ParamField>

<ParamField path="max_replication_slots=4" type="setting">
How many bookmarks may exist at once. One per Debezium connector, plus headroom for manual testing.
</ParamField>

<ParamField path="max_wal_senders=4" type="setting">
How many processes may stream WAL concurrently.
</ParamField>

<ParamField path="wal_sender_timeout=0" type="setting">
Disables disconnecting idle consumers. Convenient on a laptop where you pause work; **not** what you would set in production.
</ParamField>

The publication is created in SQL, once per database:

```sql sql/claims/02_cdc.sql
CREATE PUBLICATION dbz_claims
    FOR TABLE claim, claim_status_history, claim_transaction, adjuster;
```

## The slot does not exist yet

Nothing is being captured right now. Publications and `wal_level` make capture *possible*; the slot is what makes it *happen*, and **Debezium creates the slot when the connector is first registered**.

Until then, changes are written to WAL and discarded at the next checkpoint, exactly as they would be on any ordinary database.

## Watching the log yourself

You can see the raw change stream without Debezium, using the human-readable `test_decoding` plugin:

<Steps>
  <Step title="Create a temporary slot">
    ```sql
    SELECT pg_create_logical_replication_slot('manual_peek', 'test_decoding');
    ```
  </Step>
  <Step title="Make a change">
    ```sql
    UPDATE policyholder SET city = 'Kharadi' WHERE policyholder_id = 1;
    ```
  </Step>
  <Step title="Read the log">
    ```sql
    SELECT * FROM pg_logical_slot_get_changes('manual_peek', NULL, NULL);
    ```

    You will see `BEGIN`, the `UPDATE` with its old key and new tuple, then `COMMIT`. This is precisely what Debezium consumes — it just uses the `pgoutput` plugin, which carries the same information in binary.
  </Step>
  <Step title="Drop the slot">
    ```sql
    SELECT pg_drop_replication_slot('manual_peek');
    ```
  </Step>
</Steps>

<Warning>
**Never leave a slot behind.** An inactive slot keeps its promise — Postgres will retain WAL for a consumer that is never coming back, until the disk fills and the database stops accepting writes. "An orphaned replication slot filled the disk" is a genuine production incident and a common interview question.

Check what each slot is holding:

```sql
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_retained
FROM pg_replication_slots;
```
</Warning>
